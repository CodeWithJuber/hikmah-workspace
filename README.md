Self-hosted chat, coding, agents and experimental context learning. This is the **v9.1 release candidate**, ported from the v9 app to Node.js for deployment on your own server. It includes the v8 provider/free-model fixes.

The app version and research version are deliberately separate:

| Label                             | Meaning                                              |
| --------------------------------- | ---------------------------------------------------- |
| App v9.1                          | This self-hosted application release                 |
| Build `<commit>`                  | Exact source revision compiled into the running app  |
| Context Field · Research model v6 | Existing research dataset and learned parser release |

The sidebar, sign-in screen and `/api/health` identify the application release. A v6 research label does not mean the app has reverted to v6.

## What is included

- Streaming chats, coding workspace and sandboxed HTML preview, model comparison, resumable agent activity and readable provider explanations.
- OpenRouter and supported OpenAI-compatible providers. OpenRouter defaults to **free-only**; paid model requests are rejected while that setting is enabled. Provider availability and rate limits still apply.
- Custom agent profiles, tool permissions and MCP connection settings; browser JavaScript sandbox, reference search and webpage reading.
- Personal memory with review, owner-published shared knowledge, inspectable learning feedback and a context-model training/release center.
- Existing research corpus, reproduction scripts, language models, data provenance and capability notes under `public/research`.
- Private owner login with Better Auth, SQLite persistence and local object storage. No ChatGPT authentication headers are trusted on this host.
- Docker, Caddy HTTPS, GitHub Actions, image checksums, health checks and a deployment rollback path.

The context model is an experimental structured parser, not a general language model. Quranic roots are a research representation and design lens; this repository does not establish that every language derives from Arabic or that the system has human-level intelligence. Provider explanations and concise activity records are shown; hidden chain-of-thought is not collected or stored.

## Quick start

Use Node 24.15 or newer in the Node 24 line. The lockfile is committed.

```bash
npm ci --ignore-scripts
cp .env.example .env.local
```

Set `BETTER_AUTH_SECRET` to a new value generated by `openssl rand -hex 32`, and set your owner email in `.env.local`. Use `BETTER_AUTH_URL=http://localhost:3000` locally. Do not commit that file.

Create `.data/bootstrap-owner-password` containing a new password of 12–128 characters; use a password manager or enter it without shell-history recording. Restrict the directory to mode 700 and the file to mode 600. The file is consumed and removed after the owner account is created.

```bash
npm run setup
npm run dev
```

`npm run dev` builds the browser sandbox worker first (`npm run build:worker`); it is build output and is not committed.

For a production build on a local machine:

```bash
npm run build
npm start
```

Public registration is disabled. The initial deployment is a private owner workspace. Self-service signup, email delivery, billing and organization administration need separate implementation before a public SaaS launch.

## Verify

```bash
npm test
npm run typecheck
npm run build
npm run test:production
python3 -m unittest discover -s public/runtime -p 'test_*.py'
python3 -m unittest discover -s deploy -p 'test_*.py'
```

The production smoke test stages the standalone build in an isolated directory, signs in, rejects spoofed identities and cross-origin writes, saves a large conversation, restarts the server, and verifies both the session and saved content. No model provider is called by these tests.

## Deploy to your own server

See [deployment instructions](docs/deployment.md) for the server requirements and the GitHub Actions settings. This project is independent of `hikmah-stack` and does not require changing it.

GitHub Actions builds and tests the image on GitHub-hosted runners. With deployment enabled, the deploy workflow takes that same verified image, copies it to your server over SSH with a deploy key, checks its revision, takes a local pre-update backup, and starts the app behind HTTPS. It verifies the exact commit again through the public URL.

Credentials, private conversations, `.data`, installed dependencies and build output are never part of the repository. Export saved sessions from an earlier installation and import them after signing in; the app does not migrate another host's database or model checkpoints automatically.

## Tools and services

| Capability                                            | Availability                                                                                                       |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Local JavaScript sandbox, calculator, workspace files | Built into the app                                                                                                 |
| Web reference search and webpage reading              | Server routes; require outbound network access                                                                     |
| Terminal, `bash`, `sandbox_run`, `ssh_exec`           | The `workbench` service. Nothing runs without it; the app container cannot host a shell or a pty                   |
| Python/Node execution and approved SSH actions        | Legacy path: runtime adapter in `public/runtime`, deployed separately. Superseded by the workbench                 |
| Voice dictation and read-aloud                        | Browser support and user microphone permission required                                                            |
| Image/audio/video generation                          | Requires a configured provider and an available allowed model; no paid generation was used for validation          |
| MCP servers                                           | Seeded catalogue under Connections. Remote servers connect from the app; command-line servers run in the workbench |

The app container has no Docker socket or host SSH credentials, and the workbench
holds no secrets of its own. Commands run in the workbench container, which has a
writable `/workspace` and network access but no route to the app's database or
its encrypted secrets. See `docs/architecture.md` for the trust boundaries, what
is gated behind an approval and why, and what is deliberately not built.
